# 任务 4.4：网页内远程桌面（noVNC），用于在 K8s 中完成平台登录

先阅读 `AGENTS.md`、`docs/REFACTOR_PLAN.md` 的“阶段 4 的具体决定”、4.3 完成的 `server/platform-login/`、`server/routes/platform-login.js`、`server/auth/guard.js`、`server/auth/session.js`，以及部署仓库 `~/playwright-upload-deploy/scripts/start-desktop.sh`（现有容器桌面：Xvfb `:99` + openbox + x11vnc `localhost:5900`，以前用 websockify 暴露在 6080，**这次要去掉对外暴露**）。

## 背景
本机开发时，4.3 的有头登录浏览器直接出现在本机屏幕上。部署到 K8s 后，浏览器运行在容器的虚拟屏幕（Xvfb）上，用户看不到。以前的做法是通过 NodePort 6080 暴露 noVNC，**没有任何认证**，任何能访问端口的人都能操作浏览器。

本任务改为：VNC 只监听容器内 `127.0.0.1:5900`；用户浏览器通过**后端鉴权后的 WebSocket** 访问，后端把 WebSocket 数据原样转发到 `127.0.0.1:5900` 的 TCP 连接（相当于内置一个只给已登录用户用的 websockify）。

依赖已安装：后端 `ws@8`，前端 `@novnc/novnc@1.7.0`（ESM，入口 `core/rfb.js`）。**不要再安装任何包。**

## 要做的事

### 1. 显示模式配置（`server/platform-login/display.js`）
- 环境变量 `RUYI_LOGIN_DISPLAY`：
  - 未设置或 `local`（默认）：本机开发模式，登录浏览器直接显示在本机屏幕，不提供远程桌面
  - `vnc`：容器模式，登录浏览器显示在 `DISPLAY`（如 `:99`）上，后端提供 WebSocket 转发；VNC 地址 `RUYI_VNC_HOST`（默认 `127.0.0.1`）、`RUYI_VNC_PORT`（默认 `5900`）
- `vnc` 模式下 `RUYI_VNC_HOST` 只允许 `127.0.0.1` / `localhost` / `::1`，否则启动失败（防止误配置成转发到任意地址）
- `publicSession` 增加字段 `display: 'local' | 'vnc'`

### 2. WebSocket 转发 `server/platform-login/vnc-proxy.js`
- 路径：`GET /api/platform-login/:id/vnc`（WebSocket 升级）
- 用 `ws` 的 `WebSocketServer({ noServer: true })`，在 Fastify 底层 `app.server` 的 `upgrade` 事件中处理，只处理这一个路径，其他路径的升级请求直接 `socket.destroy()`
- 升级前必须校验（复用 `server/auth/` 的工具，不要另写一套）：
  1. 读取 Cookie `ruyi_session`，按 `guard.js` 相同规则找到有效会话和用户；`mustChangePassword` 用户拒绝
  2. `Origin` 头必须与请求的 `Host` 同源（防止跨站 WebSocket 劫持）；缺少 Origin 拒绝
  3. 登录会话存在、属于该用户、`status` 为 `starting` 或 `waiting`、显示模式为 `vnc`
  4. 同一个登录会话同时只允许一条 VNC 连接；新连接到来时关闭旧连接
  - 任一失败：写入 `HTTP/1.1 401 Unauthorized`（或 403/404/409）并销毁 socket，不升级
- 转发：`net.connect(port, host)`，WebSocket 二进制消息 ↔ TCP 数据双向原样转发；任一端关闭则关闭另一端；单条消息上限 4MB
- 登录会话结束（succeeded/failed/cancelled/expired）时，主动关闭它的 VNC 连接
- WebSocket 子协议：noVNC 客户端会请求 `binary`，服务端在握手时选择 `binary`
- 转发流量**不写日志、不写操作记录**（只在连接建立和断开时写服务日志一行，不含数据）

### 3. 登录浏览器在 vnc 模式下的启动
- `vnc` 模式：`chromium.launch({ headless: false, env: { ...process.env, DISPLAY: process.env.DISPLAY || ':99' }, args: ['--start-maximized', '--window-position=0,0', '--window-size=1280,800'] })`；上下文 viewport 1280×800
- 同一个 X 显示上同时只能清楚地显示一个人的登录窗口，所以 **vnc 模式下全局同时只允许 1 个登录会话**（覆盖 `RUYI_MAX_LOGIN_SESSIONS`），超出时返回 409 `有其他用户正在登录平台，请稍后再试（约 N 分钟）`，N 为当前会话剩余超时时间向上取整
- `local` 模式保持 4.3 的行为

### 4. 前端组件 `web/src/components/RemoteDesktop.vue`
- props：`sessionId`
- 使用 `import RFB from '@novnc/novnc'` 连接 `${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/api/platform-login/${sessionId}/vnc`
- `rfb.scaleViewport = true`、`rfb.resizeSession = false`、`rfb.background = '#15211f'`
- 显示连接状态文字（连接中 / 已连接 / 已断开，可点击重连）
- 组件卸载时 `rfb.disconnect()`
- 本任务只做组件，**接入页面在 4.5 做**；但要确保 `npm --prefix web run build` 能成功打包 noVNC（noVNC 1.7 含顶层 await，若 Vite 构建报错，在 `web/vite.config.js` 中设置 `build.target: 'es2022'` 和 `optimizeDeps.esbuildOptions.target: 'es2022'`，这是唯一允许的 vite 配置改动）

### 5. 开发代理
`web/vite.config.js` 的 `/api` 代理增加 `ws: true`，使开发模式下 WebSocket 也能转发到后端。

### 6. 测试 `test/vnc-proxy.test.js`（数据库测试 `ruyi_test`，加入 `test:all`）
启动一个**本地假 VNC 服务**（`net.createServer` 监听 `127.0.0.1` 随机端口，收到什么就回显什么，前面加固定前缀以便区分），用 `RUYI_LOGIN_DISPLAY=vnc`、`RUYI_VNC_PORT=<随机端口>` 启动 app 并 `listen({ port: 0, host: '127.0.0.1' })`，用 `ws` 客户端连接。登录会话用 4.3 的注入方式造一个 `waiting` 状态的假会话（不启动真实浏览器）。覆盖：
- 正确 Cookie + 同源 Origin：连接成功，发送二进制数据收到回显（经过假 VNC 服务）
- 无 Cookie / 伪造 Cookie → 握手失败（401）
- Origin 缺失或不同源 → 握手失败（403）
- 用户 B 连接 A 的会话 → 失败（404）
- 会话不存在 / 已结束 → 失败
- 第二条连接到来时第一条被关闭
- 会话被取消后，已建立的连接被服务端关闭，假 VNC 服务端的 TCP 连接也被关闭
- 其他路径的升级请求（如 `/api/status`）被拒绝
- `RUYI_VNC_HOST=10.0.0.1` 时 `vnc` 模式启动失败
- vnc 模式下第二个用户开始登录 → 409
- 测试结束关闭所有服务器和连接，不遗留端口
