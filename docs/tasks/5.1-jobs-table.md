### 1. 迁移文件 `db/migrations/20261020_005_create_jobs.js`
写法与已有迁移一致（`sql` 模板，`up` 建表，`down` 删表），必须通过 `db/migration-guard.js`（`node scripts/migrate.js plan` 不连库也能检查）。

```sql
CREATE TABLE ruyi_jobs (
  id               CHAR(36)        NOT NULL COMMENT '任务 ID（UUID），同时作为 RUYI_JOB_ID 传给脚本',
  user_id          BIGINT UNSIGNED NOT NULL,
  username         VARCHAR(32)     NOT NULL COMMENT '启动时的用户名快照',
  task             ENUM('upload','create','analyse','download') NOT NULL,
  status           ENUM('queued','running','succeeded','failed','cancelled','interrupted') NOT NULL DEFAULT 'queued',
  headless         TINYINT(1)      NOT NULL DEFAULT 1 COMMENT '启动时的运行模式',
  request_id       CHAR(36)        NULL COMMENT '与操作记录关联',
  claim_token      CHAR(36)        NULL COMMENT 'Worker 认领时写入',
  worker_id        VARCHAR(128)    NULL,
  cancel_requested TINYINT(1)      NOT NULL DEFAULT 0,
  exit_code        INT             NULL,
  exit_signal      VARCHAR(16)     NULL,
  error_message    VARCHAR(1000)   NULL,
  state_refreshed  TINYINT(1)      NOT NULL DEFAULT 0,
  state_expired    TINYINT(1)      NOT NULL DEFAULT 0,
  log_path         VARCHAR(255)    NULL COMMENT '相对用户工作区的日志文件路径',
  queued_at        DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  started_at       DATETIME(3)     NULL,
  finished_at      DATETIME(3)     NULL,
  heartbeat_at     DATETIME(3)     NULL COMMENT 'Worker 每 15 秒更新一次',
  PRIMARY KEY (id),
  KEY idx_status_queued (status, queued_at),
  KEY idx_user_queued (user_id, queued_at),
  KEY idx_user_status (user_id, status),
  CONSTRAINT fk_ruyi_job_user FOREIGN KEY (user_id) REFERENCES ruyi_users (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='任务队列'
```

### 2. 数据访问 `server/repos/jobs.js`（第一个参数为 `db`；只用 Kysely 查询构建器或 `sql` 模板）

**命名锁工具**：`withClaimLock(db, fn, { timeoutSeconds = 5 })`
- 用 `db.connection().execute(async (conn) => { ... })` 固定**同一个连接**
- `SELECT GET_LOCK('ruyi_job_claim', ?) AS acquired`；未获得锁（0 或 NULL）时返回 `null`，不执行 `fn`
- 获得后执行 `fn(conn)`，最后**无论成功失败**在同一连接上 `SELECT RELEASE_LOCK('ruyi_job_claim')`

函数：
- `enqueueJob(db, { id, userId, username, task, headless, requestId, maxPerUser = 5 })`
  - 在 `withClaimLock` 内：统计该用户 `status IN ('queued','running')` 的数量，达到 `maxPerUser` 时返回 `{ ok: false, reason: 'user_limit' }`；否则 INSERT，返回 `{ ok: true }`
  - 拿不到锁时返回 `{ ok: false, reason: 'busy' }`
- `claimNextJob(db, { workerId, claimToken })` → 认领到的任务行或 `null`
  - 在 `withClaimLock` 内：
    1. 选出候选：`status='queued' AND cancel_requested=0`，并且该用户**没有** `status='running'` 的任务（`NOT EXISTS` 子查询，SELECT 中引用同表是允许的），按 `queued_at, id` 取第一条
    2. `UPDATE ruyi_jobs SET status='running', claim_token=?, worker_id=?, started_at=NOW(3), heartbeat_at=NOW(3) WHERE id=? AND status='queued'`
    3. 受影响行数为 1 时，按 `id` 查出整行返回；否则返回 `null`
  - **禁止** `SKIP LOCKED`、禁止在 UPDATE 中子查询 `ruyi_jobs`（MySQL 5.7 报 1093）
- `heartbeat(db, { workerId })`：该 Worker 所有 `running` 任务 `heartbeat_at = NOW(3)`
- `finishJob(db, { id, claimToken, status, exitCode, exitSignal, errorMessage, stateRefreshed, stateExpired, logPath })`
  - `status` 只能是 `succeeded` / `failed` / `cancelled`
  - `WHERE id=? AND claim_token=? AND status='running'`；`finished_at = NOW(3)`；返回是否更新成功
  - `errorMessage` 截断到 1000 字符
- `setLogPath(db, { id, claimToken, logPath })`
- `requestCancel(db, { id, userId })` → `'cancelled'`（原本在排队，直接改为 `cancelled`、写 `finished_at`）、`'cancelling'`（原本在运行，设 `cancel_requested=1`）、`'finished'`（已结束，不变）或 `null`（不存在或不属于该用户）。排队→取消必须是带 `status='queued'` 条件的原子 UPDATE，避免与认领竞争
- `listCancelRequested(db, { workerId })` → 该 Worker 中 `status='running' AND cancel_requested=1` 的任务
- `recoverStaleJobs(db, { staleSeconds = 60 })`：把 `status='running' AND heartbeat_at < NOW(3) - INTERVAL ? SECOND` 的任务改为 `interrupted`，`error_message='服务重启或异常退出，任务已中断'`，`finished_at=NOW(3)`；返回被中断任务的 `{ id, userId, username, task, requestId }` 列表（供写操作记录）。先 SELECT 出 id，再 `UPDATE ... WHERE id IN (...) AND status='running' AND heartbeat_at < ...`
- `getJob(db, id)`、`getJobForUser(db, id, userId)`
- `queuePosition(db, job)`：返回排在它前面的 `queued` 任务数（全局，按 `queued_at, id`）；不是 `queued` 时返回 0
- `listJobs(db, { userId, page, pageSize })`：按 `queued_at DESC, id DESC`；返回 `{ items, total }`；`userId` 为空时列出全部（管理员用）
- `activeJobForUser(db, userId)`：该用户最近的一条 `queued` 或 `running` 任务（前端恢复显示用）
- `hasRunningJob(db, userId)`

### 3. 测试 `test/jobs-repo.test.js`（数据库测试 `ruyi_test`；保护与清理同 `test/platform-state.test.js`，清理时注意先删 `ruyi_jobs` 再删 `ruyi_users`；加入 `test:all`，脚本名 `test:jobs-repo`）
- 入队、认领：认领后 `status='running'`、有 `claim_token`、`started_at`
- 同一用户两个排队任务：第一个认领后，第二次 `claimNextJob` 返回 `null`；第一个结束后能认领第二个
- 两个用户各一个任务：可以先后认领两个
- **并发认领**：同时调用 `claimNextJob` 10 次（`Promise.all`，用不同 `claimToken`），只有符合条件的任务被认领，且同一任务不会被认领两次、同一用户不会有两个 `running`
- `maxPerUser`：第 6 个任务返回 `user_limit`
- `finishJob` 用错误的 `claimToken` 返回 false 且状态不变
- 取消排队任务 → `cancelled`，之后不能被认领；取消运行中任务 → `cancelling` 并出现在 `listCancelRequested`；取消已结束任务 → `finished`；用户 B 取消 A 的任务 → `null`
- `recoverStaleJobs`：把某运行中任务的 `heartbeat_at` 改到 2 分钟前 → 变为 `interrupted`；心跳新鲜的不受影响
- `queuePosition`、`listJobs` 分页与 `total`、`activeJobForUser`
- 命名锁：在另一个连接上先 `GET_LOCK('ruyi_job_claim', 0)` 占住，`enqueueJob`（`timeoutSeconds` 设为 1）返回 `busy`；释放后正常；测试结束确认 `IS_FREE_LOCK('ruyi_job_claim') = 1`
