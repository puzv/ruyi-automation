# 7.5 自动轮询平台并推进后续任务

## 背景

当前流水线每一步都要用户手动点击（上传 → 创建人群包 → 人群洞悉 → 下载），而平台处理上传文件、生成人群包、生成洞悉结果都需要等待几分钟到几十分钟。用户点完一步就得反复回来手动“检测当前状态”再点下一步，实际使用中大量时间花在盯页面上。

负责人要求：加入轮询机制，让有平台待处理文件的用户自动查询平台，一旦没有待处理就自动往下推进；洞悉结果就绪后停止等待，由用户自行下载。

负责人确认的两项决策：
- 推进范围：上传后自动推进到结果就绪（上传仍由用户手动点击触发）。
- 开关默认值：默认开启，用户可手动关闭。

## 范围

只推进到“洞悉结果就绪”，不自动下载：

| 工作区状态 | 平台探测 | 动作 |
|---|---|---|
| `createCount > 0` | 按类型检查上传文件是否处理完 | 全部就绪 → 自动排队 `create` |
| `analyseCount > 0` | 检查人群包是否生成完 | 全部就绪 → 自动排队 `analyse` |
| `doneCount > 0` | 检查洞悉结果是否生成完 | 全部就绪 → **停止轮询**，等用户手动下载 |

运行状态（当前阶段、下次检查时间、停滞计数）放内存，重启后按工作区文件与平台状态重新推导；数据库只保存开关。

## 安全边界（每一次探测都要启动无头浏览器，必须严格限流）

1. 只在当前阶段确实有待办时才探测；无待办直接 `idle`。
2. 同一用户同时只允许一个任务，排队或运行中一律不探测。
3. 复用 `state.platformProbes`，避免与用户手动“检测当前状态”同时启动浏览器。
4. 只对近期有任务活动的用户生效（`ACTIVITY_HOURS`，默认 12 小时，当前是代码常量而非环境变量），避免服务重启后替用户补做很久以前的待办。
5. 状态连续 `maxStalled`（默认 20 次）没有变化 → 置 `stalled` 并停止。
6. 自动提交的任务跑完但待办签名没变（脚本没推进清单）→ 置 `stalled` 并停止，不重复提交。
7. 洞悉结果就绪 → `nextCheckAt = Infinity`，彻底停止。
8. 平台登录态缺失或检查报“登录/未打开成功” → `loginRequired`，5 分钟后重试。
9. 后台探测强制 `headless: true`，不受用户“调试模式”开关影响。
10. 自动提交同样写 `job.start` 操作记录，`detail.auto = true` 便于区分。

1. 打开工作台，确认出现“自动推进”面板且开关默认开启。
2. 手动点击“上传文件”，上传完成后不要点任何按钮，观察面板：

   - 文件处理完 → 自动排 `create`，面板显示“平台文件已就绪，正在创建人群包”

4. 断开平台登录态，确认面板显示“平台登录已失效，请重新登录”并给出登录入口，5 分钟后再试。
5. 服务重启后确认引擎按工作区与平台状态重新推导，不会替当天没操作过的用户启动浏览器。

## 运行期修复（2026-10-22）

线上实测暴露了三个问题，均与「自动推进」与既有逻辑的边界有关。

### 1. 前端自行探测与自动推进抢占位，409 被显示成「读取失败」

`pollJob` 在 upload/create/analyse 成功后会自动调用 `detectCurrentStatus()`，而自动推进的 `onFinished` 几乎同时唤醒引擎探测同一用户。两者共用 `state.platformProbes`，前端因此拿到 409，`detectCurrentStatus` 把所有非 ok 当成失败，界面显示「平台状态读取失败」。

修复：`pollJob` 先取自动推进开关，`enabled` 时改为 `POST /api/auto-advance/check` 让服务端立即接管，不自己探测；关闭自动推进时保持原行为。同时 `detectCurrentStatus` 对 409 做 3 次短重试，仍 409 时提示「自动推进仍在检查平台」而不是「读取失败」。

回归测试：`test/frontend-jobs.test.js` 断言自动推进开启时 `/api/platform-status` 调用次数为 0、`/api/auto-advance/check` 为 1；关闭时为 1 和 0。已验证移除修复后该用例失败。

### 2. 人群包尚未进入列表时被误判为「已就绪」

`inspectAnalyseAudience` 只统计「找到且状态为 PROCESSING」的记录。刚提交的人群包有一段延迟才出现在列表里，此时返回 0，`decide()` 判为 `readyAnalyse`，导致过早提交人群洞悉。

修复：新增 `countPendingAudiences` / `countPendingAudiencesTotal`，记录实际找到的目标，**没找到的一律计入未就绪**，并打印「尚未出现在列表中，继续等待」。

### 3. 洞悉结果记录缺失时被误判为「已就绪」

`inspectInsightResults` 中 `latest` 为 `undefined` 时 `latestStatus` 是空串，不在 `activeStatuses` 里，于是被判为完成并停机，用户看到并不存在的下载。

修复：新增 `pendingInsightResult(latest, activeStatuses)`，`!latest` 或状态为空一律算未就绪。

回归测试：新增 `test/platform-inspect.test.js`（8 组断言，不启动浏览器），覆盖未出现、计算中、`frontStatus`、全部 SUCCESS、名称空白归一、记录缺失、状态大小写、未知状态。已接入 `npm run test:results`。
