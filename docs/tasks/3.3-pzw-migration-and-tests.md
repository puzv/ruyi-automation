# 任务 3.3：pzw 数据迁移与阶段 3 验收测试

先阅读 `AGENTS.md`、`docs/HANDOFF.md`、`docs/REFACTOR_PLAN.md`、`docs/tasks/3.1-workspace-and-jobs.md`、`docs/tasks/3.2-platform-name-manifest.md`，以及现有迁移脚本和测试约定。

## 要做的事

1. 新增一次性本地迁移脚本，将共享数据根目录下现有 `upload/` 工作区归入 `users/pzw/`；默认先做冲突检查和预览，只有明确执行迁移动作时才复制或移动文件。
2. 迁移脚本不能读取或打印本任务之外的敏感文件，不能修改已有数据库迁移；对目标目录已存在、文件冲突、路径越界和 JSON 无法解析给出中文错误并停止。
3. 迁移后保留原始文件名和现有 JSON 清单语义，不主动给旧文件改平台名称；阶段 3 的新任务才使用用户名、类型、任务 ID 和序号命名。
4. 增加不依赖真实浏览器的端到端隔离测试：两个用户导入相同与不同文件、任务列表互不可见、同一任务重复初始文件名被拒绝、结果恢复名和路径越界均符合预期。
5. 更新必要的任务脚本或测试脚本入口，但不把数据库测试接入无数据库的 `npm test`；阶段完成前运行 `npm run test:all`。

## 迁移方式

- 实现必须支持 dry-run；具体执行迁移前由主代理依据负责人已确认的 `pzw` 归属和当前工作区状态选择安全方式。
- 不得删除原 `upload/`，除非负责人另行明确授权；优先采用可回滚的复制方案并在输出中列出文件数量和冲突。
- 负责人已指定旧数据归属 `pzw` 并要求完成阶段 3，实际迁移采用复制：默认源为现有 `config.uploadRoot`，目标为 `<root>/users/pzw/`，递归复制时严格排除 `users/` 以及本次迁移的临时目录，防止自递归。不删除、不覆盖源或目标，不打印文件内容。开发脚本和测试只能使用人工临时样本；真实旧数据只由主代理在审查通过后运行该脚本复制。
- 迁移实现不得读取 `.env`、登录态、浏览器 Profile 或连接数据库；复制文件的字节校验可以通过流式哈希实现但不输出数据。已有目标需明确检测，不得静默合并覆盖。
- 实现分两步：先写迁移脚本及独立测试，待 3.1 和 3.2 实现完成后再整合专项测试和 `package.json`，避免改动重叠；同一共享测试库的数据库测试由主代理串行执行。
- 现有 `.gitignore` 中登记的历史 `conclusion/` 结果目录也纳入复制白名单；`.gitignore` 增加 `/upload/users/`，避免新用户运行数据进入版本控制。其他未知根目录条目保守报错，不静默忽略数据。
- 实际预检发现根目录另有普通文件 `总结报告生成流程.md`。作为旧工作区的配套说明，仅将这一确切名称加入辅助文件白名单，按原字节复制并校验，不解析其内容；不放开任意 Markdown 文件或未知目录。

## 完成标准

- `pzw` 用户可以使用迁移后的工作区，其他用户不能读取其中内容。
- 阶段 3 专项测试和 `npm run test:all` 通过。
- 主代理能够列出实际改动文件、敏感文件哈希校验结果、测试命令和剩余平台页面验证风险。
