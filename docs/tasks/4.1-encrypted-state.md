先阅读 `AGENTS.md`（特别是“登录态”一节）、`docs/REFACTOR_PLAN.md` 的“阶段 4 的具体决定”、`db/migrations/20251020_004_create_platform_states.js`、`server/repos/`（写法参考）、`server/audit.js`。

- 不安装依赖（只用 Node 自带 `crypto`）。

## 要做的事

### 1. 加密工具 `server/platform-state/crypto.js`
- `loadKeys(env = process.env)`：读取 `RUYI_STATE_KEY`（必填，base64，解码后必须正好 32 字节）和可选的 `RUYI_STATE_KEY_PREVIOUS`（同格式，用于换密钥）。返回 `{ current: { version, key }, previous?: { version, key } }`。版本号：`RUYI_STATE_KEY_VERSION`（默认 1）；旧密钥版本 `RUYI_STATE_KEY_PREVIOUS_VERSION`（默认 current - 1）。格式错误时抛中文错误，**错误信息中不得包含密钥内容**。
- `encryptState(stateObject, userId, keys)` → `{ ciphertext: Buffer, keyVersion }`
  - AES-256-GCM，每次随机 12 字节 IV，16 字节认证标签
  - 存储格式：`iv(12) + tag(16) + 密文`
  - AAD：`Buffer.from(\`ruyi-platform-state:v1:user:${userId}\`)`
- `decryptState(ciphertext, keyVersion, userId, keys)` → 对象；按 `keyVersion` 选择 current 或 previous；认证失败（包括 userId 不匹配）抛 `登录态解密失败`，不暴露底层错误细节
- `estimateExpiry(stateObject)`：在 cookie 中找这些关键名字，取其中**最早**的 `expires`（秒级时间戳，`-1` 或缺失表示会话 cookie，忽略）：`dn_token`、`gdt_token`（任一域）、`ndmp_token`、`SSO_SESSION_ID`。返回 `Date` 或 `null`。

### 2. 数据访问 `server/repos/platform-states.js`
表结构已存在（`ruyi_platform_states`，每个用户一行，`uk_user`）。函数（第一个参数为 `db`）：
- `getStateRow(db, userId)`：返回整行或 `undefined`
- `saveCapturedState(db, { userId, ciphertext, keyVersion, expiresHintAt, platformAccount })`：用户扫码登录后保存。不存在则 INSERT（`captured_at = NOW()`、`last_verified_at = NOW()`、`status='valid'`、`version=1`）；存在则 UPDATE 同样字段并 `version = version + 1`。用 `INSERT ... ON DUPLICATE KEY UPDATE` 一条语句完成（MySQL 5.7 支持；用 Kysely 的 `onDuplicateKeyUpdate`）
- `refreshState(db, { userId, expectedVersion, ciphertext, keyVersion, expiresHintAt })`：任务成功后回写。`UPDATE ... SET ..., refreshed_at=NOW(), last_verified_at=NOW(), version=version+1 WHERE user_id=? AND version=? AND status='valid'`；返回是否更新成功（受影响行数为 1）
- `markExpired(db, { userId, expectedVersion })`：`status='expired'`，同样带版本条件
- `clearState(db, userId)`：用户主动清除：`status='expired'`、`state_ciphertext=NULL`、`version=version+1`（**不 DELETE**）

### 3. 服务层 `server/platform-state/index.js`
把加密和数据访问组合起来，供后续任务使用：
- `loadUserState(db, userId, keys)` → `null`（无记录、已过期或密文为空）或 `{ state, version, expiresHintAt, capturedAt, refreshedAt, lastVerifiedAt }`
- `storeCapturedState(db, userId, state, keys, { platformAccount })`
- `storeRefreshedState(db, userId, expectedVersion, state, keys)` → 是否成功
- `getStatusSummary(db, userId)` → `{ status: 'none' | 'valid' | 'expired', capturedAt, refreshedAt, lastVerifiedAt, expiresHintAt }`。**不返回密文和明文**；`valid` 但 `expiresHintAt` 已过当前时间时，`status` 返回 `'expired'`

### 4. 启动时校验
`server/index.js`：启动时调用 `loadKeys()`，失败则打印中文错误并以非 0 退出（与缺少数据库配置的处理方式一致）。把 keys 传给 `buildApp({ db, stateKeys })`，`buildApp` 用 `app.decorate('stateKeys', ...)` 挂载（`auth: false` 时可不传）。

### 5. 状态接口
`GET /api/platform-state`（需登录）→ `{ ok: true, ...getStatusSummary }`。注册在 `server/routes/platform-state.js`。只读接口，不写操作记录。

### 6. 测试 `test/platform-state.test.js`（数据库测试，`ruyi_test`，保护与清理方式同 `test/server-auth.test.js`；加入 `test:all`）
- 加密后解密得到原对象；两次加密同一对象密文不同（IV 随机）
- 篡改密文任一字节、换 userId 解密、用错误密钥解密 → 都抛 `登录态解密失败`
- 换密钥：用旧密钥（version 1）加密的数据，在 `current=v2, previous=v1` 配置下仍能解密
- `loadKeys`：缺失、非 base64、长度不是 32 字节 → 抛错，且错误信息不包含传入的值
- `estimateExpiry` 取关键 cookie 中最早的过期时间，忽略会话 cookie 和无关 cookie
- 仓库：首次保存 version=1，再次保存 version=2；`refreshState` 版本不匹配时返回 false 且数据不变；`markExpired` 后 `loadUserState` 返回 null；`clearState` 后密文为 NULL 且行仍存在
- 数据库中的 `state_ciphertext` 不包含伪造 cookie 的明文值（例如 cookie value 设为 `PLAINTEXT_MARKER_123`，断言库中密文不含该字符串）
- `GET /api/platform-state`：未登录 401；登录后无记录为 `none`；保存后为 `valid`；响应体不含 `cookies`、`ciphertext`、`PLAINTEXT_MARKER_123`
