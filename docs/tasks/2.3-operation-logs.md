# 任务 2.3：操作记录

先阅读 `AGENTS.md`、`docs/REFACTOR_PLAN.md`、`db/migrations/20251020_003_create_operation_logs.js`，以及 2.2 完成的 `server/auth/`、`server/routes/`、`server/routes.js`、`server/jobs.js`。

## 本地环境
同 2.2（测试库 `ruyi_test`，环境变量传入，不读 `.env`，不安装依赖）。

## 原则
- `ruyi_operation_logs` **只追加**：业务代码中只允许 `INSERT` 和 `SELECT`，不得 `UPDATE` / `DELETE`（测试清理 `ruyi_test` 除外）。
- 写记录失败**不能影响业务请求**：捕获异常，用 `app.log.error` 记录后继续。
- `detail` 中**不得出现**密码、令牌、Cookie、登录态、文件内容。

## 要做的事

### 1. 记录工具 `server/audit.js`
- `writeLog(db, entry, log)`：`entry` 字段 `{ userId, username, action, targetType, targetId, result, errorMessage, detail, ip, userAgent, requestId }`；`detail` 序列化为 JSON；`errorMessage` 截断到 1000 字符，`targetId` 截断到 255，`userAgent` 截断到 255
- `sanitizeDetail(value)`：递归删除键名匹配 `/password|token|cookie|secret|state/i` 的字段；字符串值截断到 500 字符；数组最多保留 100 项
- `auditFromRequest(request, entry)`：从 `request.user` 补 `userId`/`username`，从请求补 `ip`、`userAgent`、`requestId`
- `requestId`：每个请求用 `crypto.randomUUID()` 生成一次（惰性生成并挂在 request 上）

### 2. 要记录的动作
| action | 位置 | target | result / detail |
|---|---|---|---|
| `auth.login` | 登录接口 | — | 成功 / 失败；失败时 `detail.reason` 为 `unknown_user` / `wrong_password` / `locked` / `disabled` / `invalid_request`；`username` 记录尝试的用户名（截断到 32），用户存在时写 `userId` |
| `auth.logout` | 退出 | — | 成功 |
| `auth.password_change` | 修改密码 | — | 成功 / 失败，失败时 `detail.reason` |
| `admin.user_create` | 管理员 | `user` / 新用户名 | 成功 / 失败；`detail.role` |
| `admin.user_disable` / `admin.user_enable` / `admin.password_reset` | 管理员 | `user` / 被操作的用户名 | 成功 / 失败 |
| `file.import` | `POST /api/import-folder` | `file_batch` / 空 | 成功 / 失败；`detail` 为 `{ count, skipped, files: [导入的文件名] }`（最多 100 个） |
| `job.start` | `POST /api/run/:task` | `job` / 任务 ID | 成功（任务已启动）/ 失败（被 409/404 拒绝时也记，`detail.reason` 为返回的提示）；`detail.task` |
| `job.finish` | 任务子进程结束时 | `job` / 任务 ID | 退出码 0 为成功，否则失败；`detail` 为 `{ task, code, signal, durationMs }`；`requestId` 与对应的 `job.start` 相同；用户为启动任务的用户 |
| `platform.login_open` | `POST /api/login-open` | — | 按接口结果；`detail.opened` |
| `profile.release` | `POST /api/profile-release` | — | 按接口结果；`detail.terminatedJobs` 数量 |
| `runtime.mode_change` | `POST /api/runtime-mode` | — | 成功；`detail.headless` |
| `admin.logs_view` | 管理员查询记录（见下） | `user` / 查询的用户名，未指定则空 | 成功；`detail` 为查询条件 |

- 只读的 GET 接口（status、login-status、platform-status、jobs、me、users 列表、mine）不记录。
- `job.finish` 需要在 `server/jobs.js` 的 `startJob` 中增加可选回调参数（例如 `startJob(task, script, { onFinish })`），由路由传入写记录的函数；不改变子进程启动参数和已有行为。服务关闭后子进程才结束时，写记录失败只打日志。
- `auth: false` 模式（旧测试用）下不写记录，也不能报错：没有 `app.db` 时 `writeLog` 直接跳过。

### 3. 查询接口（`server/routes/logs.js`）
- `GET /api/logs/mine?page=1&pageSize=20&action=` → 当前用户自己的记录（按 `user_id` 过滤），按 `id` 倒序
- `GET /api/admin/logs?username=&action=&result=&from=&to=&page=&pageSize=` → 管理员查询全部
  - `from` / `to` 格式 `YYYY-MM-DD`，按北京时间整天计算：`created_at >= from 00:00:00` 且 `< to 的次日 00:00:00`；格式错误返回 400
  - `username` 精确匹配快照字段 `username`
  - 查询时写一条 `admin.logs_view`，但只在**第 1 页**时写，避免翻页刷记录
- 两个接口：`pageSize` 默认 20，最大 100；`page` 从 1 开始；返回 `{ ok: true, items, total, page, pageSize }`；`items` 字段用驼峰，`detail` 返回解析后的对象；**不返回** `userAgent`（管理员接口可以返回 `ip` 和 `userAgent`，普通用户接口只返回 `ip`）
- 不使用 MySQL 8 语法（窗口函数等）；`total` 用单独的 `COUNT(*)` 查询
