# 任务 5.2：Worker 与任务接口

先阅读 `AGENTS.md`、`docs/REFACTOR_PLAN.md`（“阶段 5 的具体决定”）、5.1 完成的 `server/repos/jobs.js` 和迁移文件，以及现有的 `server/jobs.js`（阶段 4 的登录态临时文件、回写、过期标记逻辑）、`server/routes.js` 中 `/api/run/:task` 与 `/api/jobs/:id`、`server/index.js`、`server/app.js`、`server/audit.js`、`server/platform-state/`。

## 目标
认证模式下，任务不再由 HTTP 请求直接启动，而是：**接口只负责入队，Worker 负责认领并执行**。任务记录与日志持久化，服务重启不丢失。`auth: false` 模式保持原有内存实现不变（只供旧测试）。

## 本地环境
测试库 `ruyi_test`（5.1 已在其中建好 `ruyi_jobs`）；不读 `.env`；不安装依赖。

## 要做的事

### 1. 任务执行器 `server/worker/runner.js`
把 `server/jobs.js` 中“启动一次任务”的逻辑抽出来复用（**不要复制一份**，抽成两边都能用的函数；`auth: false` 的内存路径继续使用它）。`runJob({ job, db, keys, log, dataRoot, signal })`：
1. 读取用户：`users.findById(db, job.user_id)`；用户不存在或已停用 → 任务 `failed`，`error_message='用户不存在或已停用'`
2. 加载登录态：`loadUserState`；没有可用登录态 → `failed`，`error_message='请先完成平台登录'`（**入队时也会检查一次，这里是二次确认**，因为排队期间登录态可能过期或被清除）
3. 工作区：`ensureWorkspace(resolveWorkspace(user, dataRoot))`
4. 日志文件：`<工作区>/logs/<任务ID>.log`（目录不存在则创建，文件权限 600，`flag: 'wx'`），`log_path` 存相对工作区路径 `logs/<任务ID>.log`。子进程 stdout/stderr 追加写入该文件。**日志中不得写入登录态、临时路径**（脚本自身输出除外）
5. 环境变量与阶段 4 相同：`RUYI_JOB_ID=job.id`、`RUYI_USER`、`RUYI_UPLOAD_DIR`、`RUYI_HEADLESS`（用 `job.headless`，不再读全局 `state.headlessMode`）、`RUYI_STATE_FILE`（临时目录 700 / 文件 600）
6. **进程包装**：用 `scripts/job-wrapper.js` 启动脚本，而不是直接启动脚本：
   - 包装器以 `detached: true` 启动（独立进程组），通过 `process.argv` 拿到要运行的脚本，用 `spawn` 运行它（`stdio: 'inherit'`）
   - 包装器与 Worker 之间用 IPC 通道（`stdio: ['ignore', 'pipe', 'pipe', 'ipc']`）：包装器监听 `process.on('disconnect')`，**Worker 退出（包括崩溃、被 kill -9）时 IPC 断开，包装器立即对自己的进程组发 SIGTERM，5 秒后 SIGKILL**，确保不会留下孤儿脚本继续改写用户文件
   - 正常结束时包装器以脚本的退出码退出
7. 取消：`signal`（AbortSignal）触发时，对任务进程组发 SIGTERM，5 秒后 SIGKILL；结果状态为 `cancelled`
8. 结束：按阶段 4 规则处理登录态（logged-out 标记 → `markExpired`；内容变化 → `storeRefreshedState`），删除临时目录（无论成功失败）；返回 `{ status, exitCode, exitSignal, errorMessage, stateRefreshed, stateExpired }`。退出码 0 → `succeeded`，否则 `failed`；被取消 → `cancelled`

### 2. Worker `server/worker/index.js`
`createWorker({ db, keys, log, dataRoot, workerId = \`${os.hostname()}:${process.pid}\`, maxConcurrent, pollMs = 1000 })`，返回 `{ start(), stop(), wake() }`：
- 循环：当前运行数 < `maxConcurrent`（默认读 `RUYI_MAX_CONCURRENT_JOBS`，默认 2）时调用 `claimNextJob`；认领到就 `runJob`，结束后 `finishJob`（用 `claim_token`），并写操作记录 `job.finish`（`detail` 与阶段 4 相同，加上 `queuedMs`），登录态过期时额外写 `platform.state_expired`。操作记录的 `userId`/`username`/`requestId` 取自任务行
- 没有可认领任务时等待 `pollMs`；`wake()` 立即唤醒（入队接口调用，减少等待）
- 每 15 秒 `heartbeat`；每 2 秒检查 `listCancelRequested`，对这些任务触发取消
- `start()` 时先调用一次 `recoverStaleJobs({ staleSeconds: 60 })`，对每个被中断的任务写操作记录 `job.finish`（`result='failure'`、`detail.status='interrupted'`）；之后每 30 秒再调用一次（另一个 Worker 崩溃时由存活的 Worker 回收）
- `stop()`：停止认领；对所有运行中的任务发取消，等待它们结束（最多 10 秒），这些任务记为 `interrupted`（`finishJob` 增加对 `interrupted` 的支持，或在 5.1 的函数上扩展，修改需在报告中说明），然后返回
- `finishJob` 返回 false（说明任务已被其他 Worker 回收为 interrupted）时，只记服务日志，不再写 `job.finish`

### 3. 接入方式
- `server/index.js`：`RUYI_WORKER` 不为 `off` 时，`app.listen` 成功后创建并启动 Worker（内嵌模式，用户启动方式不变）；`app.close()` 前先 `worker.stop()`
- 新增 `server/worker/main.js`：独立运行 Worker（加载 `.env`、`loadKeys`、`createDb`，处理 SIGTERM/SIGINT 调用 `stop()`）；`package.json` 增加 `"worker": "node server/worker/main.js"`
- `buildApp` 增加选项 `worker`（可为空）；入队后调用 `app.worker?.wake()`

### 4. 接口（认证模式）
- `POST /api/run/:task`：
  - 未知任务 404（不变）
  - 检查登录态：没有可用登录态 → 409 `PLATFORM_LOGIN_REQUIRED`（不变）
  - `enqueueJob`（`headless` 取当前 `state.headlessMode`）：`user_limit` → 409 `排队任务过多，请等待已有任务完成`；`busy` → 503 `服务繁忙，请稍后重试`
  - 成功 → `{ ok: true, id, status: 'queued', position }`
  - **不再**因为全局并发或同用户已有任务而拒绝（改为排队）
  - 操作记录 `job.start` 保持（`detail.task`；新增 `detail.queued: true`）
- `GET /api/jobs/:id`：返回 `{ ok: true, job }`，`job` 字段：`id, task, status, position, queuedAt, startedAt, finishedAt, exitCode, errorMessage, cancelRequested, running`（`running` 为 `status === 'running'`，兼容旧前端）、`code`（等于 `exitCode`，兼容旧前端）、`output`（日志文件**最后 64KB** 的内容，文件不存在为空字符串）。不属于自己 → 404
  - **兼容**：旧前端直接读顶层的 `running`、`code`、`output`，所以响应顶层也展开这三个字段：`{ ok: true, job, running, code, output }`
- `GET /api/jobs/:id/log`：返回完整日志（`text/plain; charset=utf-8`），超过 5MB 时只返回最后 5MB 并在开头加一行 `（日志过长，仅显示最后 5MB）`；不属于自己 → 404
- `GET /api/jobs?page=&pageSize=`：自己的任务列表（字段同上，不含 `output`），`{ ok, items, total, page, pageSize }`
- `GET /api/jobs/active`：自己当前排队或运行中的任务（最多 1 条，供前端刷新后恢复），没有则 `{ ok: true, job: null }`
- `POST /api/jobs/:id/cancel`：`requestCancel`；返回 `{ ok: true, result }`（`cancelled` / `cancelling` / `finished`）；不属于自己 → 404。写操作记录 `job.cancel`
- `GET /api/admin/jobs?username=&status=&page=&pageSize=`：管理员查看全部任务（字段同列表，加 `username`）
- 路由顺序注意：`/api/jobs/active` 必须在 `/api/jobs/:id` 之前匹配
- `POST /api/import-folder` 的“当前用户有任务运行时拒绝导入”：改为查询数据库 `hasRunningJob`（排队中的任务不拦截导入；运行中拦截）
- `web/src/labels.js` 增加 `job.cancel: '取消任务'`

### 6. 测试 `test/worker.test.js`（数据库测试 `ruyi_test`；加入 `test:all`，脚本名 `test:worker`）
**不启动真实浏览器与业务脚本**：通过参数注入替换要运行的脚本（例如 runner 接受 `scriptPath` 映射或 `spawnImpl`），测试中用 `test/fixtures/fake-job.js`：根据环境变量 `FAKE_JOB_MODE`（`ok` / `fail` / `sleep` / `rewrite-state` / `logout`）打印几行输出、可选改写 `RUYI_STATE_FILE`、可选写 `.logged-out` 标记，然后以对应退出码退出。覆盖：
- 入队 → Worker 认领 → 成功：状态 `succeeded`、`exit_code=0`、日志文件存在且内容正确、权限 600、`GET /api/jobs/:id` 的 `output` 有内容、`job.finish` 记录写入
- 失败退出：`failed`
- 同一用户连续入队 3 个：依次执行，任何时刻该用户最多一个 `running`
- `maxConcurrent=2`，3 个用户各 1 个：前两个同时运行，第三个排队（`position`=1），前面结束后自动开始
- 取消排队中的任务：不会被执行
- 取消运行中的任务（`sleep` 模式）：进程组被终止，状态 `cancelled`
- **Worker 被强制终止时任务进程也结束**：在子进程中启动一个独立 Worker（例如 `node test/fixtures/worker-child.js`），让它认领一个 `sleep` 任务，记录脚本的 PID（假脚本把 PID 写进日志），对 Worker 子进程发 `SIGKILL`，断言 6 秒内该脚本 PID 不再存在；再启动一个新 Worker 的 `recoverStaleJobs`（`staleSeconds` 设小）把该任务改为 `interrupted`
- 登录态：`rewrite-state` 模式后 `version+1`；`logout` 模式后状态 `expired`；临时目录在所有情况下被删除
- 排队期间用户被停用 / 登录态被清除：任务 `failed`，提示正确
- 接口：`GET /api/jobs`、`/api/jobs/active`、`/api/jobs/:id/log`（超长截断）、`/api/jobs/:id/cancel`、`/api/admin/jobs`（普通用户 403）；用户 B 访问 A 的任务全部 404
- 日志和接口响应中不包含伪造 cookie 值和临时目录路径

已有测试（`test/job-state.test.js`、`test/server-isolation.test.js`、`test/server-audit.test.js` 等）若因“直接运行”改为“入队”而失败，按新行为更新，并在报告中逐条列出修改。
