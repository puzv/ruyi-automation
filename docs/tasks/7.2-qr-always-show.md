# 7.2 扫码登录始终显示二维码（用户决定）

在 7.1 基础上修改，不新增依赖、不改迁移。

## 决定

用户点「扫码登录」就是要重新登录，所以**无论账号是否已有有效登录态，都显示二维码**，这样也方便换账号。这一条取代 7.1 中“已有有效登录时跳过扫码”的做法。

## 修改要求

### 1. `apps/server/src/modules/platform-login/sessions.js`

- `mode === 'qr'` 时**不调用 `loadUserState`**，也不把旧登录态传给 `newContext`，浏览器上下文从空白开始。
- 同时避免旧登录态解密失败挡住重新登录。
- `mode === 'desktop'` 的行为保持不变，仍然加载已保存的登录态。

### 2. 旧登录态的保留

- 扫码成功时，用 `storeCapturedState` 覆盖旧登录态。
- 扫码失败、取消、超时或二维码多次过期时，**不得清除或修改旧登录态**，用户原来的登录继续有效。

### 3. `apps/server/src/modules/platform-login/qr.js`

- 上下文是空白的，正常情况下一定会到达登录页，保留 7.1 的“先等页面稳定”和 `selectMethod` 重试逻辑。
- 移除 7.1 中“已登录则跳过扫码”的提示文案「已有有效登录，正在确认」。如果循环里 `pageLooksLoggedIn` 为真，仍按已登录处理（这是扫码成功后的正常路径）。

### 4. 测试

- 账号已有有效登录态时发起 `mode: 'qr'`：`newContext` 不带 `storageState`，会话进入扫码，`qr` 在截到图后出现。
- 旧登录态无法解密时，扫码会话仍能正常开始。
- 扫码失败或取消后，旧登录态原样保留（比对 `version` 和密文）。
- 扫码成功后，旧登录态被新登录态替换。
- `mode: 'desktop'` 仍带 `storageState`。
- 删除或改写 7.1 中“已有有效登录态时跳过扫码”的测试。
