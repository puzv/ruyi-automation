# 任务列表按上传批次聚合

用户确认本次只考虑单批次串行流程：一个上传任务 ID 对应一个上传批次，不考虑一次执行处理多个批次。

- 保留侧栏上方登录状态入口，移除工作流导航中重复的“平台登录”。
- 上传执行的完整 UUID 为批次 ID；展示短码与文件命名一致，为 UUID 的 SHA-256 前八位。
- 后续创建、洞悉、下载归入同用户入队时间不晚于自身的最近一次上传；无上传来源的历史执行独立展示。每次新上传开始一个新批次。
- 不新增表或改动原执行记录。历史记录使用上述时间顺序规则聚合，未从历史文件反查实际关联。
- 我的任务和管理员全部任务共用批次列表，按批次分页、筛选；四步状态取各流程最新执行，展开保留全部重试记录、日志、耗时及错误。仅四步全部成功时整批显示成功，其他已结束且无错误的批次显示等待下一步。
- 个人保留执行级取消、结果重新下载、自动下载；管理员日志走仅管理员可访问的接口，管理员不能取消或下载他人结果。
- 旧 `/api/jobs` 与 `/api/admin/jobs` 默认仍返回执行记录，网页通过 `grouped=1` 请求批次视图，保持 MCP 兼容。

验证：`npm test`、前端构建；本机测试数据库可用时执行 `npm run test:jobs-repo`，覆盖分组分页、重试、历史记录、同毫秒入队和用户隔离。本次环境本机数据库连接超时，未执行数据库集成测试。

已使用本机 Chrome 无头隔离上下文、伪造空 storageState 和拦截的模拟 API 验证个人/管理员列表、四流程展开、日志接口、登录入口去重及窄屏渲染，无页面运行错误。未访问真实平台或读取真实登录态。构建输出在 `/tmp/ruyi-web-batches-20261109`，没有覆盖工作区原有 `dist` 改动。
