# 阶段 3 验收清单

本阶段不新增文件表，仍由 JSON 维护工作流；未进入阶段 4 登录态或阶段 5 Worker 队列。负责人验收通过前不进入下一阶段，不提交 git。

## 行为约定

- 后端按登录用户使用 `<RUYI_UPLOAD_DIR>/users/<用户名>/`，默认数据根为项目 `upload/`；脚本子进程接收用户实际目录，前端不能指定其他目录。
- 导入保留初始文件名；多次导入及不同子目录中的同名文件均保留，上传任务在任何平台操作前统一报出全部重复名称并停止。
- 新平台名称为 `<用户名>_<类型>_<任务ID短串>_<序号>`，不包含初始文件名，完整任务 ID 和名称映射保存在用户工作区 `file-manifest.json`。
- 短串取完整服务端任务 ID 的 SHA-256 前 8 位十六进制字符；生成名称发生碰撞或超过平台 30 字符限制时在上传前报错，不截断用户名或静默复用平台对象。较长用户名可能因此无法启动上传任务。
- 创建、洞悉、下载使用分配好的平台名，重试不重新分配；下载恢复初始主文件名，保留结果格式后缀（如 `.xlsx`），不覆盖已有结果。
- 所有用户仍共用 Profile，全局只运行一个浏览器任务；用户只能查询自己的任务和日志，管理员的操作记录查询权限按阶段 2 保留。
- 旧数据归 `pzw`，复制后原目录保留；旧清单不改平台名称，不能追溯恢复历史已丢失的初始名称。

## 负责人逐步验收

先重启当前后端服务加载新代码（开发模式为 `npm run dev:server`），保留原来的运行方式和端口；验收使用网页登录后的用户工作区。

1. 准备两个普通用户账号 A、B，用两个浏览器会话分别登录；导入人工测试样本，文件名包含 `pn`、`idfa` 或 `oaid`，格式为 `.txt`/`.csv`。管理员允许释放其他用户任务，不适用于第 3 步的普通用户权限检查。
2. A 导入一个文件，确认 A 待上传数量增加、B 不变；B 也导入同名文件，确认两者互不覆盖，页面计数各自独立。
3. A 启动上传；B 启动任意浏览器任务应提示已有任务运行。用 A 返回的任务 ID 在 B 会话请求 `/api/jobs/<ID>`，应为 404，不能看到 A 的输出；B 点击释放 Profile 也不能停止 A 的任务。
4. 对新上传文件检查平台显示名：包含用户名、正确类型、任务短串、序号；原始文件名只在本地映射里；同一任务多个同类型文件的序号不同。用户名中包含 `pn` 时，`idfa` 文件仍应进入 IDFA 流程。
5. 连续执行创建人群、洞悉、下载；确认每一步使用同一平台名，最终结果恢复原始主文件名和实际结果后缀。若同名结果已存在，应失败且保留待下载任务，已有文件内容不能改变。
6. 在同一用户下分两次导入同名文件，或选择两个子目录中的同名文件；点击上传应一次性提示重复原始文件名并停止，不能静默改名或上传其中一份。测试完成后自行整理该测试用户的重复样本，再继续上传。
7. 中断或失败后重试上传，检查 JSON 映射中的平台名、原始名、上传任务 ID 沿用原记录，不能产生第二套平台名；新加入的不同文件分配新的唯一名称。
8. 使用 `pzw` 账号确认迁移的历史待处理数量和结果可用；B 不应看到这些数量和文件。历史清单继续使用旧平台名，新导入任务使用新命名规则。
9. 退出 A 再登录 B，确认任务输出和状态不串用；未登录访问工作台 API 仍返回 401。
