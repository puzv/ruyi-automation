# 重构计划

目标：把单人本地工具改造成部署在 K8s、多人使用、数据按用户隔离、有操作记录的平台。

分工：Claude Code 负责规划、拆分任务、审查与验收；Codex 负责按任务说明编写代码（阶段 3 曾由 Codex 主代理统筹，阶段 4 起由 Claude Code 重新统筹）；
每完成一个阶段，由项目负责人亲自验收后再进入下一阶段。

## 已确定的技术决定
| 项目 | 决定 |
|---|---|
| 后端 | Node.js + Fastify，CommonJS JavaScript，放在 `server/` |
| 前端 | Vue 3 + Vite，保留在 `web/`，只负责页面；开发时代理 `/api` 到后端 |
| 自动化脚本 | 保留现有 Playwright 脚本，后续阶段再改为可调用的函数 |
| 数据库 | 远程共享库 `bsg_dw`（MySQL 5.7），Kysely，表名前缀 `ruyi_` |
| 平台登录态 | storageState，AES-256-GCM 加密存入 `ruyi_platform_states` |
| 本系统登录 | 账号密码（bcrypt）+ 服务端会话 `ruyi_user_sessions` + httpOnly Cookie |

## 阶段

### 阶段 1：后端独立（功能不变）
把 `web/vite.config.js` 里的 API 拆成独立的 Fastify 服务，前端改为生产构建，由后端统一提供。
- 1.1 搭建 `server/`：Fastify 启动、提供 `web/dist` 静态文件、`/api/health`、npm 脚本
- 1.2 逐个迁移现有 10 个接口，路径、请求和返回格式保持不变
- 1.3 `web/vite.config.js` 只保留 Vue 插件和开发代理；清理 `RUYI_DEBUG_NAV` 诊断代码；更新 README
- 1.4 接口测试
- **验收**：构建并启动后，网页的状态显示、导入文件、运行任务、登录检测与改造前一致

### 阶段 2：用户登录与操作记录
- 用户登录 / 退出 / 修改密码，会话校验，登录失败锁定
- 命令行创建管理员；管理员创建、停用用户、重置密码
- 操作记录中间件；“我的操作记录”和管理员查询页面
- **验收**：未登录无法访问；不同用户登录后只看到自己的操作记录

阶段 2 的具体规则（已按建议值确定）：
- 账号由管理员创建，不开放注册；新建或重置密码后首次登录必须修改密码
- 密码 bcrypt（bcryptjs，cost 12），至少 8 位
- 连续登录失败 5 次锁定 15 分钟；用户名不存在与密码错误返回同一提示
- 会话：闲置 8 小时过期，最长 7 天；Cookie `ruyi_session`，httpOnly、SameSite=Lax；修改密码、停用账号时撤销该用户全部会话
- 数据库配置从 `.env` 读取；本地开发库为 Docker 中的 MySQL 5.7（`ruyi_dev`，测试用 `ruyi_test`）
- 任务拆分：2.1 数据访问层与命令行建管理员 → 2.2 登录接口与鉴权 → 2.3 操作记录 → 2.4 前端登录与记录页面

### 阶段 3：用户数据隔离
- 每个用户独立目录 `<数据根目录>/users/<用户名>/`；数据根沿用 `RUYI_UPLOAD_DIR`（默认项目 `upload/`），脚本子进程收到的是该用户实际工作区
- 不新增文件清单数据库表；继续使用三个 JSON 任务清单，另存 `file-manifest.json` 记录平台名称、初始文件名、类型、完整上传任务 ID 与序号
- 平台名称不包含初始文件名，采用 `<用户名>_<类型>_<任务ID短串>_<序号>`，不超过平台 30 字符限制；上传重试沿用已有映射，后续流程使用同一平台名称
- 上传前检查整个任务的全部待处理文件是否有重复初始文件名，提示重复后停止；下载结果恢复初始主文件名并保留实际结果格式扩展名，不覆盖已有结果
- 任务及日志按用户隔离；阶段 3 仍全局只运行一个浏览器任务（共享 Profile），不提前实现阶段 4 登录态或阶段 5 Worker 队列
- 现有共享 `upload/` 数据归属 `pzw`，迁移采用复制并保留源文件，历史清单与旧平台名称兼容
- 任务拆分：3.1 用户工作区与任务隔离 → 3.2 平台名称与初始文件名映射 → 3.3 pzw 数据迁移与阶段验收测试
- **验收**：两个用户互相看不到对方的文件、任务和结果；同名检查、上传名称唯一性、下载结果恢复和重试均符合约定

### 阶段 4：平台登录态改造
- 登录态加密存库；任务按用户加载登录态；过期检测与提醒
- 临时登录桌面（按需分配，经后端鉴权访问），替换原 Profile 登录流程
- **验收**：用户在网页内完成平台登录，之后运行任务无需 Profile

阶段 4 的具体决定（Claude Code 重新接管统筹，2026-10-19）：
- 每个用户一份登录态，存 `ruyi_platform_states`，AES-256-GCM 加密，AAD 绑定 `user_id`；密钥来自环境变量 `RUYI_STATE_KEY`（32 字节 base64），不入库、不入仓库
- 任务子进程拿到的是**临时解密文件**（权限 600，任务结束即删除），通过已有的 `RUYI_STATE_FILE` 机制加载；任务结束后服务端把子进程回写的新登录态重新加密入库（乐观锁 `version`），检测到已退出登录时标记 `expired`
- 平台登录在**服务端临时有头浏览器**中完成：本机开发时窗口直接出现在本机桌面；K8s 中运行在 Xvfb 上，经 noVNC 嵌入网页。VNC 只监听 127.0.0.1，浏览器通过后端鉴权的 WebSocket 访问，不再暴露 6080 端口
- 登录判断沿用 `lib/storage-state.js` 的强判断（业务元素持续 3 秒），弃用 `inspectLoginStatus` 的弱判断
- 放开并发：不同用户的任务可以同时运行（各自独立浏览器）；同一用户仍只允许一个任务；全局上限 `RUYI_MAX_CONCURRENT_JOBS`（默认 2）
- 移除 Profile 相关功能：`/api/login-open`、`/api/profile-release`、“释放 Profile”按钮；`ruyi-profile/` 在验收通过后由负责人自行删除
- 任务拆分：4.0 修正阶段 3 遗留问题 → 4.1 登录态加密存储 → 4.2 任务按用户加载登录态并放开并发 → 4.3 服务端登录会话与登录检查 → 4.4 网页内远程桌面（noVNC）→ 4.5 前端改造与清理 Profile 代码

### 阶段 5：任务队列与 Worker
- 任务入 `ruyi_jobs` 表，Worker 独立进程认领执行；人群文件流水线状态入表
- **验收**：重启服务不丢任务记录；多人任务排队执行

阶段 5 的具体决定（2026-10-20，负责人同意先做 5A）：
- **5A 任务队列（本阶段）**：任务入 `ruyi_jobs` 表；脚本输出写入用户目录 `logs/<任务ID>.log`；满员时排队而不是拒绝；重启后排队任务继续执行，运行中的任务标记为“已中断”；可查看历史任务与完整日志；可取消排队中或运行中的任务
- **5B 流水线入表（以后）**：JSON 清单与 `file-manifest.json` 暂不入表，等做“分析下载文件”功能时再做
- Worker 默认**内嵌在 `npm start` 的进程里**（用户启动方式不变）；也可单独运行 `npm run worker`，API 设置 `RUYI_WORKER=off`，供阶段 6 拆分部署
- 认领任务：在 MySQL 命名锁 `GET_LOCK('ruyi_job_claim')` 内“选出候选 + 原子 UPDATE（`WHERE status='queued'`）+ claim_token”，保证多个 Worker 下同一用户也只有一个运行中任务（MySQL 5.7 不支持 SKIP LOCKED，且 UPDATE 不能子查询同表）
- 并发：每个 Worker 同时最多 `RUYI_MAX_CONCURRENT_JOBS`（默认 2）个；同一用户同时只运行 1 个，其余排队；每个用户排队+运行中最多 5 个
- 任务进程用包装器启动：Worker 退出（包括异常退出）时任务进程组随之结束，避免孤儿脚本继续改写文件
- `auth: false` 模式保留原内存实现，只供旧测试
- 任务拆分：5.1 任务表与认领 → 5.2 Worker 与接口 → 5.3 前端任务页面

### 阶段 6：部署
- 更新 Dockerfile 与 K8s 配置（API、Worker、登录桌面、Secret、Ingress）
- **验收**：在开发网 K8s 上完成以上全部验收项
